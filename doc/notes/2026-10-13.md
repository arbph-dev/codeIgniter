Understood — focus on validating the register → activation flow end‑to‑end. Step‑by‑step here, slow and practical, with exact checks and commands you can run now. I’ll assume you have the browser DevTools and access to the server logs.

End‑to‑end happy path (what should happen)
User fills register form → client publishes auth:register
Controller posts POST /api/auth/register
Server responds { email_verified: false, message: "..." } (pending)
Controller sets authStore.pendingEmail and publishes auth:register:pending
UI shows register‑pending screen with an activation input
User enters code → client publishes auth:activate with token
Controller posts POST /api/auth/activate with { email, token }
Server returns 200 { message: "Compte activé..." }
Controller publishes auth:activated → UI shows success and returns to login form
User can now login (POST /api/auth/login returns token + user)

If activation fails — quick diagnostics
A. Activation request not sent or wrong payload

Network tab: confirm /api/auth/activate is called and request body contains both email and token.
If token alone is sent (no email) but server expects email+token, activation will fail. The code already uses authStore.pendingEmail when calling fetchActivate; confirm authStore.pendingEmail is set.
B. Server returns 4xx / unexpected HTML

Capture response body and status (Network tab → click request → Response).
If server responds with HTML (Shield redirect flow), you may see 302 or opaqueredirect. In that case:
Either your server expects a session-based verify (/auth/a/verify) — problematic across page reloads — or
Use the /api/auth/activate approach (JSON { email, token }) which is implemented in auth.service.fetchActivate.
If you see a 422/429, copy the JSON error text and the request payload.
C. Token accepted but login still fails (403)

Possible cause: activation endpoint used Shield session (server-side) rather than API activation, so account is not actually activated.
Inspect server logs (writable/logs/*) for activation errors or for Shield behavior.
Reproduce with curl to be sure of server behavior (see commands below).
