### 📊 Objectif

POST /api/auth/magic-link { email }
- crée l'identité magic-link (secret aléatoire et expiration) et envoie un lien vers la SPA, par exemple https://zealot.fr/?magic=....

POST /api/auth/magic-link/verify { token } 
- supprime l'identité (usage unique), vérifie l'expiration et que le compte est actif, puis renvoie un access token comme login().

POST /api/auth/password (avec token) { new_password }
- permet de changer le mot de passe après connexion.

Cela réutilise **UserIdentityModel** et la logique de **MagicLinkController**, sans toucher aux pages natives.

##### 🎯 cas à valider
 Il reste quelques cas à valider avant de passer à la suite :

- Mauvais code. Attendu : 422 {"error":"Code d’activation invalide ou expiré."}. Le message doit s'afficher dans le board avec le champ de code conservé.
- Limitation. Au sixième essai en une minute, attendu : 429. Si vous n'obtenez jamais de 429, le cache est probablement sur dummy (Config\Cache) et le Throttler ne compte rien.
- Renvoi du code. Il suppose le bouton .auth-resend dans AuthPanelBase. Attendu : 200 avec le message générique, puis un nouvel email, l'ancien code devenant invalide.
- Compte déjà activé. Rejouer activate sur un compte actif doit renvoyer 200 « Compte déjà activé », ce qui évite une erreur si l'utilisateur clique deux fois.
- Session résiduelle. Après une inscription suivie d'une activation sans rechargement, /login natif ne doit pas rediriger vers auth-action-show. C'est le test du nettoyage de session dans activate().
